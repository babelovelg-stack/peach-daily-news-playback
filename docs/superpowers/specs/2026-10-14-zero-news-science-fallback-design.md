# 零合格新闻时的儿童科普版设计

状态：用户于 2026-10-26 确认修复并恢复每日云端发送；本文保留已确认的设计边界，实施与部署进展见对应实施计划及实际运行证据。

## 用户确认的边界

- 仅当原定滚动 24 小时窗口内的合格新闻为 **0 条**时，改发儿童科学知识。
- **1 条合格新闻不切换**；仍按现有新闻版质检处理。正常日报至少需要 2 条、2 个独立来源，所以正常日报只有 1 条时仍不发送。测试、合并补发模式的既有门槛不在本次变更中调整。
- 不降低新闻质量，不用旧闻或低质量稿件凑数，不接入新的模型服务，不添加依赖电脑的定时任务。
- 科普版包含 3 条可靠、适龄、近期未重复的儿童科学知识，并保留探索题、上一期答案及语音。科普本身不合格时整期不发送。

## 设计时的代码事实（实施前）

- `peach-daily-news.mjs` 已有无新闻时的解释文案，但生成后的新闻数量门禁会阻止发送。
- 生成器内部质量检查与 `peach-news-self-check.mjs` 是两道检查，不能只修改其中一道。
- 现有百科池有适龄表达、标签、ID 和文本去重检查，但没有统一的逐条原始资料元数据，不直接把所有百科视为已核验的科学资料。
- 正常日报、测试、合并补发均使用同一云端发送链路；合并补发目前单日最少新闻数与正常日报不同，本次不顺带改变历史规则。
- 发送完成后才写入正式状态；播放页、音频、字幕、播报文本均需先发布并校验。
- 实际发信入口 `send-existing-peach-email.mjs` 在没有新闻标题时提前返回、跳过播放内容校验，且自行重建邮件主题；新科普版必须同步适配这个入口。

## 决策和失败边界

| 检查结果 | 模式 | 后续行为 |
| --- | --- | --- |
| 0 条逐条检查合格的新闻 | `science` | 选择 3 条通过检查的科普，继续整期校验 |
| 1 条逐条检查合格的新闻 | `news` | 不切换；沿用当前运行模式的数量和来源门槛 |
| 2 条及以上合格新闻 | `news` | 沿用新闻版全部门槛 |
| 科普、题目、语音、发布、邮件或状态读写失败 | 不做二次降级 | 停止并保留失败信息，不伪装成功 |

“合格新闻”指通过现有时效、内容价值、适龄解释、标题正文一致性、来源要求及去重检查的候选。先逐条剔除不合格候选并记录原因，再决定模式；不能为了触发科普而清空仍合格的新闻。来源多样性、数量等整期失败不是“零新闻”。

链接检查在模式决策前完成。确定失效的文章链接按逐条不合格处理；超时、429、5xx 等暂时无法验证的结果应重试，仍不能验证则停止本次运行，不把技术异常宣称为新闻全部质检未过。采集需要记录成功与失败：成功抓取但没有适合内容可判为零新闻；全部来源抓取失败、编辑数据解析错误、程序异常都不触发科普兜底。

## 内容与呈现

- 使用仓库内可审阅的科普资料池，首批内容在实施时逐条核对权威机构原始资料；每条包含稳定 ID、科学知识点标识、标签、适龄正文、来源名称、原文 URL 和核验日期。不靠正文长度或链接可打开来代替事实核验。
- 每期选择 3 条不同科学知识点，覆盖不同主题；复用现有历史 ID 和文本去重，并补充知识点去重。资料不足时停止，不清空历史或重复旧内容。
- 科普是常识内容，不套用新闻 24 小时发布时间限制，也不伪称当天新发现；新闻窗口仍为前一天 18:00 后至当天 18:00。
- 科普版邮件主题、正文和播放页明确标注“儿童科学知识版”，说明“本期没有通过质量检查的新闻，来读三条儿童科学知识”。不输出空新闻区块、新闻来源数量或“今日科学新发现”。
- 这 3 条科普替代当期“博物小百科”内容区，不额外再重复放 3 条。每条在邮件和页面提供大人核对的来源链接。
- Xiaoyi 语音播报开场、科普和结尾，仍不播报探索题或答案；语速、音高、页面布局和收件人不变。

## 结构与审计

- 增加独立的模式决策与科普质量模块，供生成器和命令行自检复用；不对大主文件做无关重构。
- 每个日期的审计记录增加 `contentMode`、模式决策证据（候选数、合格数、逐条拒绝原因及采集状态）、科普条目与来源、相关去重历史。科普分支必须具有明确的零合格证据，不能只凭任意模式字段跳过新闻检查。
- 新审计版本严格验证模式、证据与内容一致性：`science` 必须没有新闻、有 3 条合格科普；`news` 始终调用现有新闻门禁。不能把全局 `minimumNewsCount` 改成 0。旧版本审计只按旧新闻规则读取，不自动获得科普豁免。
- 两道检查都校验科普结构、来源、数量和去重；来源链接在生成及发送前自检中核验。探索题等非新闻失败不触发科普替换。
- 单日生成与合并补发按每个日期独立决策，并按顺序累积科普去重历史；合并展示清楚区分各日期模式。历史已准备邮件重发仍走原校验链路，不因为这个功能补造或改写旧内容。
- `send-existing-peach-email.mjs` 的新科普版正常发送与重发必须读取并验证新审计记录、保留科普主题，校验邮件、页面与播报的模式、日期、3 条科普一致性，并核验全部四个已发布文件；不能因为没有新闻标题而跳过检查。新科普重发产物必须携带审计与四文件校验依据，缺失或无法验证则拒绝发送。旧新闻产物维持兼容，不扩展为旧版空新闻邮件放行。
- 正式状态新增末期模式与科普知识点历史，保留现有新闻历史；成功发送科普也更新该日期的发送状态，防止当晚重试再次发送。失败不更新正式状态，不在科普发送后自动追加一封同日新闻。
- 云端的生成 → 自检 → 发布四文件 → 线上逐字节核验 → 发信 → 保存状态顺序不变。无需新密钥或模型接口。

## 验收

1. 0 条新闻（成功采集为空、候选全部内容不合格、候选全部过期或重复）均仅在有足够合格科普时进入科普版。
2. 1 条合格新闻明确保持新闻模式；正常日报仍因数量不足失败，既有测试和补发门槛不被顺带改写。
3. 多条合格新闻按原流程发送；来源集中、题目不合格等整期错误不触发科普。
4. 科普不足 3 条、重复知识点、缺来源、事实核验标记缺失或链接不可达均不发送；未知模式、伪造零新闻证据及旧版空新闻审计均被拒绝。
5. 全部采集失败、网络瞬态异常、状态文件损坏不被当作零新闻；使用可控测试夹具验证，不依赖当天新闻碰巧为空。
6. 邮件、HTML 页面、播报文本的日期、模式、3 条科普一致；探索题只展示不播报。合并补发有跨日期去重用例。
7. 生成或发送失败不写正式发送状态；科普发送成功后同日重试由原日期门禁拦截。
8. 执行 `npm test`，分别生成新闻版和科普版的无发送预览，再执行 `npm run self-check`；完成渲染内容核对和四文件校验。真实投递另需云端运行、发送日志、状态及线上文件证据，本设计文档本身不代表上线。
9. 通过真实发信入口的无 SMTP 测试夹具覆盖科普正常发送与重发：主题保留科普标识；零新闻仍执行播放校验；缺失或不一致的日期、模式、科普、音频、字幕、播报文本、审计均阻止发送。旧新闻重发用例保持通过。
